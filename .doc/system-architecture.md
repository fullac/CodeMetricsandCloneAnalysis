# 基于 SonarQube 与 LLM 的代码审查平台架构说明

## 1. 目标与边界
本系统用于接收源码 ZIP 包，执行 SonarQube 静态分析，提取主要缺陷，并由兼容 OpenAI 格式的大模型生成修复建议。系统仅清理本地临时源码，不删除 SonarQube 项目，以保留历史趋势数据用于长期质量观察。

## 2. 总体架构
- 前端（React + Tailwind + Monaco）
  - 上传 ZIP 与固定 `projectKey`
  - 展示上传进度与扫描结果
  - 展示缺陷上下文与 LLM 建议
- 后端（Node.js/Bun 兼容）
  - 上传接收与临时解压
  - 异步执行 `sonar-scanner`（全部通过 `-D` 参数注入）
  - 读取 Sonar Web API 主要缺陷
  - 构造精简上下文并调用 LLM
  - `finally` 清理本地临时目录
- 基础设施
  - SonarQube CE（Docker）
  - PostgreSQL（SonarQube 元数据库）
  - 本地 `sonar-scanner` CLI

## 3. 核心流程
1. 前端通过 `multipart/form-data` 上传 ZIP 与 `projectKey`。
2. 后端将 ZIP 解压到 `/tmp/review-*` 目录。
3. 后端启动子进程运行：
   - `sonar-scanner -Dsonar.projectKey=... -Dsonar.token=...`
   - 禁止落盘 `sonar-project.properties`。
4. 扫描完成后调用 `/api/issues/search` 获取 `BLOCKER/CRITICAL/MAJOR`。
5. 对每条缺陷定位文件和行号，抽取上下 10 行。
6. 将“规则+报错+精简代码片段”发送给 LLM 生成修复建议。
7. 返回聚合结果给前端。
8. `finally` 删除本地 `/tmp` 临时目录与上传 ZIP，保留 Sonar 平台项目数据。

## 4. 大模型上下文精简策略
### 4.1 精简原则
- 只发送单缺陷相关上下文，不发送整个文件。
- 仅截取 `line ±10`，保证 token 开销稳定。
- 保留行号和问题行标记，减少模型定位成本。

### 4.2 提示词约束
- 系统提示限定“输出短、可执行修复方案”。
- 用户提示结构化包含：严重级别、类型、规则、报错文本、代码片段。
- 通过低温度参数提高输出稳定性，降低幻觉风险。

### 4.3 学术汇报价值
- 可量化指标：平均每个缺陷的输入 token、耗时、建议可采纳率。
- 可做对照实验：全量源码 vs 精简上下文在成本与质量上的差异。

## 5. Sonar 历史数据留存机制
### 5.1 保留策略
- `projectKey` 由前端固定输入，保证同一项目多轮扫描汇总到同一历史曲线。
- 后端不调用删除项目 API，不执行清库动作。

### 5.2 趋势价值
- SonarQube 数据库持续积累缺陷数量、严重度分布、质量门变化。
- 可用于组会展示：版本迭代前后缺陷变化、修复速率与质量改进轨迹。

### 5.3 安全与治理
- 分析令牌仅在服务端环境变量中维护。
- 令牌仅通过命令行参数注入进程，不写入仓库文件。

## 6. 可扩展性
- 增量优化：接入 Sonar 分支/PR 分析参数，聚焦差异代码。
- 缓存优化：同一 issue key 的 LLM 结果缓存，降低重复调用成本。
- 评测闭环：引入人工确认反馈，训练“建议可采纳度”评估模型。
